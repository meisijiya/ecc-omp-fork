# ADR-0006: 插件状态与归属判定

**Date**: 2026-10-24
**Status**: accepted
**Deciders**: 本 fork 维护者

## Context

本插件贡献四类资产：skill、command、rule、agent，用户要求「禁用插件后这些资产都不该再被提供」。omp 的实现细节让这件事不能靠直觉判断：插件被禁用时文件仍留在安装根里，`skill://` 仍能解析到它；提示行里的描述是压缩描述，与 frontmatter 不一致；omp 内建的同名资产会接管名字。插件有三态：启用=提供资产，禁用=不再提供但文件仍可达，卸载=文件不可达。

## Decision

用「启用态与禁用态的差值 + 运行时解析出来的描述」判定归属与泄漏：同一轮探测里提示行条目数的差值必须等于本 fork 的 skill 总数，运行时 skill 列表里的本仓描述数必须从满变 0；command、rule、agent 按描述逐条比对。探针必须自带一条本 fork 之外的用户级对照技能与「该块是否存在」的证据，否则判为探针不可信而不是干净。启用、禁用、卸载三态语义写进安装说明。

## Alternatives Considered

### Alternative 1: 只按名字判定

- **Pros**: 实现最简单，读到名字就能下结论。
- **Cons**: 同名冲突会让判定指向错误的来源。
- **Why not**: 归属要回答「这份资产来自谁」，名字不足以区分同名资产。

### Alternative 2: 只按 `skill://` 能否解析判定

- **Pros**: 一次解析即可得到结论，探测成本最低。
- **Cons**: 禁用之后仍然能解析，会把残留当成正常提供。
- **Why not**: 可解析只说明文件可达，不说明资产还在被提供。

### Alternative 3: 用提示行条数的绝对值判定

- **Pros**: 只需一轮探测，不必在两种状态下各测一次。
- **Cons**: 别的插件增减就会误报。
- **Why not**: 只有差值能隔离出本 fork 自己的贡献。

## Consequences

### Positive
- 禁用语义有可复跑的自证脚本，结论不依赖人眼。
- 归属与泄漏可以逐条追溯到具体来源。

### Negative
- 探针要起子进程、比两轮，耗时明显高于单轮检查。
- 探针需要能临时改插件的启停状态，准备成本高。

### Risks
- 探针依赖 omp 的提示行格式与运行时 skill 列表输出，omp 升级后可能需要重新校准。
