# ADR-0002: 引用判定只有一份实现

**Date**: 2026-10-24
**Status**: accepted
**Deciders**: 本 fork 维护者

## Context

物化时必须删掉指向「本 fork 不提供的资产」的引用，否则模型会去读不存在的路径；门禁也要能判定运行树与 fork 自有资产里是否还剩悬空引用。这两件事都要回答同一个问题——这个名字在本 fork 里解不解析得出来。如果物化器和门禁各写一套启发式，两边的口径必然漂移。

## Decision

引用判定只有一份实现，放在 `tools/refscan.py`；物化器与门禁 `tools/check_refs.py` 共同调用它。

## Alternatives Considered

### Alternative 1: 物化器与门禁各写一套

- **Pros**: 两处互相独立，改一处不影响另一处。
- **Cons**: 两边口径漂移，门禁会放过物化器自己的盲区。
- **Why not**: 门禁的价值正在于用另一套检查发现物化器的漏洞，共用一套就失去意义。

### Alternative 2: 把判定内联进物化器

- **Pros**: 只有一份代码，不需要额外模块。
- **Cons**: 门禁无法复用，等于没有门禁。
- **Why not**: 门禁必须是能独立跑的检查，不能寄生在生成流程里。

## Consequences

### Positive

- 门禁与物化口径一致，同一个名字在两处得到同一个判定。
- 判定规则只需在一处演进，改动的影响面可预测。

### Negative

- 同一模块同时承担改写与判定两个角色，改动时要小心，避免把生成逻辑与检查逻辑耦合在一起。
- 想复用判定能力只能通过这个模块，不能绕开它另取一份结果。

### Risks

- 判定本身有已知盲区：只扫 markdown、不扫脚本；带点或斜杠的裸名不参与判定；前缀形式的普通词按散文放过。因此门禁退出码为 0 不等于完全自洽。
