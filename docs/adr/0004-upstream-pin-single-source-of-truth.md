# ADR-0004: 上游 pin 是唯一事实源，同步只开 PR

**Date**: 2026-10-24
**Status**: accepted
**Deciders**: 本 fork 维护者

## Context

上游资产池每周都会有变动，本 fork 需要把上游版本同步进仓库树，并在同步之后仍然满足 omp 适配，且引用门禁不报悬空引用。本机到上游 ECC 的 blob 传输不稳定，浅取经常中途断流，因此同步必须能指定具体提交、能离线复跑，还要能证明「上游 pin 指向的内容就是仓库树里那棵树」。这些约束共同要求 pin 本身可校验，不能靠人眼核对。

## Decision

`manifest/upstream.json` 是上游 pin 的唯一事实源，保存仓库、提交、版本、池摘要四个字段；`manifest/groups.json` 顶层的 upstream 块只是同步镜像，不作为独立事实源。同步脚本支持按 40 位十六进制提交强制检出，提交不可达即非零退出，绝不静默回退到远端 HEAD。定时同步之后由 CI 开 PR，不直接推默认分支，CI 在三个 profile 上依次物化并跑门禁。

## Alternatives Considered

### Alternative 1: CI 直接推默认分支

- **Pros**: 同步链路最短，不需要人工合并。
- **Cons**: 上游措辞变化会绕过评审直接进入默认分支。
- **Why not**: 上游每周变动，措辞层面的改动同样需要人看一眼，推默认分支等于取消评审。

### Alternative 2: 用版本标签代替提交

- **Pros**: 人类可读，选取上游某个发布点很直观。
- **Cons**: 标签可移动，一旦被重指向，同一份 pin 记录会指向不同内容。
- **Why not**: pin 必须等于内容，标签承担不了这个含义。

### Alternative 3: pin 只记录不校验

- **Pros**: 实现简单，同步流程不必比对内容。
- **Cons**: 无法证明池摘要与 pin 一致，pin 与仓库树可能悄悄脱节。
- **Why not**: 不可校验的 pin 只能当备忘，不能当事实源。

## Consequences

### Positive
- 每次同步可复现、可审计，pin 与仓库树内容一一对应。
- omp 适配与引用门禁在 PR 里跑，上游改动不会静默进入默认分支。

### Negative
- 同步之后要多一步合并才能进入默认分支。
- pin 与同步镜像之间的一致性需要额外维护。

### Risks
- 上游提交不可达时同步会失败；脚本失败即报错，不产生半写状态，失败只影响这一次同步尝试。
