# 事故处理与值班（incident response / on-call）

本 skill 覆盖线上事故的定级、响应流程、沟通记录、复盘与演练准备。
部署与回滚的具体操作（Dockerfile、K8s manifest、滚动/蓝绿/金丝雀策略）已由
`skill://ecc-omp-deployment-patterns`、`skill://ecc-omp-docker-patterns`、
`skill://ecc-omp-kubernetes-patterns` 覆盖，本文只引用、不复述。

---

## 何时用 / 何时不用

**何时用**
- 线上服务出现告警、错误率飙升、可用性下降。
- 用户报障或下游反馈接口异常、数据不一致。
- 需要给事故定级、拉起应急响应、分派角色。
- 需要回滚、止血或做恢复验证。
- 需要编写复盘（postmortem）报告、准备故障演练或编写 runbook。
- 参与值班、做值班交接。

**何时不用**
- 日常功能开发与需求实现——用对应语言/框架的 skill。
- 计划内变更评审——先读 `skill://ecc-omp-change-impact` 量化影响面。
- 预发布环境的普通冒烟验证——用 `skill://ecc-omp-verification-loop` 的六阶段闭环。
- 资损或敏感数据的定性处置——安全事件另走 `skill://ecc-omp-security-review` 的披露与隔离流程。

## 事故分级与响应时限

定级看三个维度：**影响面**（多少用户/请求/区域）、**是否有资损**（钱、数据丢失、合规）、**是否有绕行方案**（用户能否临时绕过）。

| 级别 | 判据（影响面 / 资损 / 绕行） | 首响时限 | 缓解时限 |
| --- | --- | --- | --- |
| **P0** | 核心功能全量不可用，或大面资损；无绕行 | ≤ 5 分钟 | ≤ 30 分钟 |
| **P1** | 核心功能严重降级，或单区域不可用；有临时绕行但成本高 | ≤ 15 分钟 | ≤ 1 小时 |
| **P2** | 非核心功能受损或错误率升高，未资损；有绕行 | ≤ 30 分钟 | ≤ 4 小时 |
| **P3** | 轻微异常、潜在隐患；无用户影响 | ≤ 2 小时 | ≤ 1 个工作日 |

定级宁可偏高：首响后 15 分钟内可下调，但不能因为定级低而错过止血窗口。
一旦涉及资损或合规，默认至少 P1，并同步 `skill://ecc-omp-security-review` 的处置口径。

## 事故流程

### 四个角色（拉群后立即分派，一人可兼多角，但指挥必须专人）

| 角色 | 职责 |
| --- | --- |
| **指挥（IC）** | 唯一决策人：定级、拍板回滚、协调资源、对外发状态；不亲手改代码。 |
| **处置** | 执行止血/回滚/修复动作，只听指挥调度。 |
| **沟通** | 对外同步：用户公告、下游通知、上级汇报，按节奏更新。 |
| **记录** | 维护时间线，逐条写「时间 / 动作 / 结果 / 决策人」，不靠事后回忆。 |

### 标准步骤

1. **发现**：告警触发或用户报障，先确认现象与范围。
2. **定级**：按上表定级，明确是否资损。
3. **拉群分角色**：建应急群，点名四个角色，指挥先到位。
4. **止血优先于定位根因**：先恢复服务（回滚、限流、切流、降级），再查根因。
   有现成回滚且近期有变更时，**直接回滚**，不要边排查边扛着。
5. **恢复验证**：用真实流量/探针确认服务回到正常水位，参考 `skill://ecc-omp-verification-loop` 的恢复判据。
6. **复盘**：事故关闭后 3 个工作日内出复盘报告（见下）。

### 什么情况必须直接回滚

- 事故前有发布/配置变更，且回滚是该变更的标准逆操作、风险已知。
- 没有一眼可见的根因，但止血手段本身就是回滚。
- 继续排查的预期耗时 > 回滚耗时，且回滚不会造成二次数据损坏。
- 多条告警指向同一最近变更。

回滚后仍需保留现场（日志、快照、复现条件）供复盘定位，不要回滚完即清理。

## 沟通与记录

### 沟通规范（每 15–30 分钟更新一次）

- **给用户**：说清楚「现在什么不能用、预计多久、有无临时方案」，不要过度承诺恢复时间。
- **给下游**：说清楚「受影响的接口/数据、是否已绕行、预计恢复窗口」，便于对方调整调用。
- **给上级**：说清楚「级别、影响面预估、已采取动作、需要的决策/资源」，结论先行。
- 状态更新统一发在应急群，避免私聊导致信息分裂。

### 绝对不要发的内容

- 未定性的根因猜测（「应该是某某服务挂了」）——容易误导且引发恐慌。
- 任何涉及安全事件的具体细节、受影响个人数据、内部排查结论——走 `skill://ecc-omp-security-review` 的披露红线。
- 指责个人的表述。

### 时间线记录规范

每条记录固定四字段，由记录角色实时写：
- **时间**（精确到分钟，用统一时区）
- **动作**（做了什么，命令或操作）
- **结果**（生效与否、指标变化）
- **决策人**（谁拍的板）

不要事故结束后凭记忆补写；补写的时间线不可信，复盘会失真。

## 演练与准备

### 发布前演练

- **回滚演练**：每次重大发布前，在预发或灰度环境实际跑一遍回滚，确认可逆、确认耗时。回滚操作步骤见 `skill://ecc-omp-deployment-patterns`。
- **故障注入**：对核心依赖做可控故障注入（断网、延时、报错），验证降级与限流是否真生效。

### runbook 要求

- **每条高频告警对应一份可执行 runbook**：写明判读方法、止血动作、回滚命令、升级路径。
- runbook 必须可照做，不依赖「记得当初怎么配的」；随架构变更同步更新。
- 慢查询/长事务类排查动作参考 `skill://ecc-omp-database-migrations` 的在线变更与回滚约束。

### 值班交接内容

- 当前未关闭的 P2+ 事故及其时间线链接。
- 已知隐患、待观察的曲线、近期变更清单。
- 谁在 on-call、升级联系人、关键系统的 runbook 位置。

## 复盘模板（postmortem）

### 原则

- **无指责（blameless）**：追问「为什么系统允许这个错误发生」，而不是「谁写的」。
- **影响面量化**：受影响用户数 / 请求数 / 错误数 / 持续时长 / 资损金额，用数字说话。
- **根因分类**：从六类里选——代码、配置、依赖、容量、流程、人。多数事故是多层叠加。
- **行动项必须带负责人与截止日期**，否则不复盘：没有 owner 和 due date 的项不会闭环。

### 可直接套用的 Markdown 骨架

```markdown
# 事故复盘：<标题>

- 级别：P0/P1/P2/P3
- 状态：已关闭
- 时间窗：<开始> ~ <恢复>
- 指挥：<name>  处置：<name>  沟通：<name>  记录：<name>

## 1. 摘要
<两句话：发生了什么、怎么恢复的>

## 2. 影响面量化
- 受影响用户数 / 请求数：
- 错误率峰值：
- 持续时长：
- 资损（如有）：

## 3. 时间线
| 时间 | 动作 | 结果 | 决策人 |
| --- | --- | --- | --- |
| | | | |

## 4. 根因
- 分类：代码 / 配置 / 依赖 / 容量 / 流程 / 人
- 直接原因：
- 深层原因（为何系统未拦截）：

## 5. 哪些做得好 / 哪些待改进

## 6. 行动项
| 序号 | 行动 | 负责人 | 截止日期 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | | | | |

## 7. 经验教训
```

## 命令样例

以下为通用表达，按实际技术栈替换 `<...>` 占位与具体工具。

1. **查最近发布记录**（git 仓库示例）
   ```bash
   git -C <repo> log --pretty=format:'%h %ci %s' -20
   ```

2. **查某服务最近错误日志**（容器/主机日志示例）
   ```bash
   kubectl logs deployment/<service> -n <ns> --since=1h | grep -i error | tail -50
   ```

3. **按时间窗拉取告警记录**（告警系统查询示例）
   ```bash
   <alert-cli> query --service <service> --from <start> --to <end> --min-severity P2
   ```

4. **确认某配置项当前值**（配置中心 / ConfigMap 示例）
   ```bash
   kubectl get configmap <cm> -n <ns> -o jsonpath='{.data.<key>}'
   ```

5. **查某次回滚是否生效**（发布平台示例）
   ```bash
   <deploy-cli> status <release-id>
   # 或比对当前镜像/版本与回滚目标
   kubectl get deployment/<service> -n <ns> -o jsonpath='{.spec.template.spec.containers[0].image}'
   ```

6. **检查长事务 / 慢查询**（PostgreSQL 示例）
   ```sql
   SELECT pid, now() - query_start AS dur, query
   FROM pg_stat_activity
   WHERE state <> 'idle' AND now() - query_start > interval '30s'
   ORDER BY dur DESC;
   ```

7. **确认近期是否有相关变更**（发布/配置时间线示例）
   ```bash
   git -C <repo> log --since="<incident_start>" --pretty=format:'%h %ci %s' -- <service-path>
   ```

## 反模式清单

1. **事故中先改代码定位，而不先止血**——把「修复」当「止血」，延长不可用时间。
2. **多人同时改同一处**——互相覆盖、无法判断哪次改动生效，指挥失去控制。
3. **复盘变成追责**——「某个人写错了」替代系统性分析，真实根因被掩盖。
4. **没有时间线，复盘靠记忆猜**——时间线缺失导致根因和顺序全凭印象，结论不可信。
5. **行动项没有负责人和截止日期**——写一堆「要加强监控」却无人跟进，下次照发。
6. **在群里发未定性的根因猜测**——引发恐慌、误导其他处置方，甚至误伤无关服务。
7. **有现成回滚却继续排查数小时**——把排查当义务，忽略回滚是已知低风险止血手段。
8. **回滚后立刻清理现场**——丢失日志与复现条件，复盘无法定位深层原因。
