# 可观测性（日志、指标、追踪、告警）

给系统建立「出了问题能知道、能定位、能复盘」的能力。三支柱各有分工，
本 skill 讲可迁移的选型口径、字段规范、指标与 SLO 口径、告警纪律和 trace_id 接入，
不绑定任何一家 SaaS（Prometheus/Grafana 等只是常见载体，做法本身是通用的）。

部署与发布动作本身看 `skill://ecc-omp-deployment-patterns`，
错误处理与兜底口径看 `skill://ecc-omp-error-handling`，本 skill 只管「看得见」。

## 何时用

- 服务要上线、要值班：没有指标和告警就上线，等于盲开。
- 故障要跨服务定位：一次用户请求经过多个服务，需要追踪把链路串起来。
- 要回答「现在能不能发布」：SLO 错误预算是发布决策的依据，不是看心情。
- 告警太多太吵、没人看：需要按症状重新设计告警。
- 新服务接入可观测性：字段规范、命名约定、trace_id 透传一次定好，避免每个服务各写一套。

## 何时不用

- 一次性脚本、本地调试、demo：`print` / 控制台输出足够，不要为它搭监控。
- 还没有真实用户流量的服务：先把日志规范做好，指标和告警等有流量、有 SLO 诉求时再上。
- 单进程、单容器、无跨服务调用的场景：日志 + 少量指标即可，追踪是负担，不必上。

## 三支柱分工与选型

| 支柱 | 回答什么问题 | 典型载体 | 成本 |
| --- | --- | --- | --- |
| 日志 | 「当时具体发生了什么」——细节、上下文、入参出参 | 日志平台 / 文件 + 采集器 | 低，但量大 |
| 指标 | 「趋势怎么样」——延迟、错误率、吞吐量、容量 | 指标系统（如 Prometheus）+ 仪表盘 | 低，长期便宜 |
| 追踪 | 「这次请求经过了哪些服务、每段花了多久」 | 追踪系统（如 Jaeger/Tempo）+ trace_id | 中，需全链路透传 |

选型口径：

- **只排查细节** → 日志。单服务问题、想知道某次请求的入参和报错栈，日志够用。
- **看趋势、定 SLO、做容量规划** → 指标。没有指标就定不了 SLO，也没有告警的依据。
- **跨服务、异步链路出问题** → 必须上追踪。当「用户报错了但不知道是哪个下游慢」发生，
  靠日志一条条 grep 拼链路是失败的做法。
- 经验线：服务数 ≤ 2 且调用是同步的，日志+指标可支撑；
  3 个以上服务互相调用，或涉及消息队列、异步任务，追踪是必需品。

## 结构化日志规范

### 字段清单

每条日志至少带这些字段（格式统一用 JSON，便于机器检索）：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| `timestamp` | 事件发生时间，UTC，带时区 | `2026-10-31T08:12:03.412Z` |
| `level` | 级别，见下表 | `warn` |
| `trace_id` | 追踪 ID，见「追踪接入」 | `a3f9...e21` |
| `service` | 服务名 | `checkout` |
| `env` | 环境 | `prod` / `staging` |
| `event` | 事件名，动词短语，可检索 | `order_created` / `payment_retried` |
| `duration_ms` | 耗时（有耗时的调用才带） | `240` |
| `error_code` | 错误码（有错误才带） | `PAYMENT_TIMEOUT` |

外加业务上下文（订单号、用户 ID 等），但注意下面的「禁止记录」。

### 日志级别与使用纪律

| 级别 | 何时用 |
| --- | --- |
| `debug` | 开发调试细节，生产默认关闭，可临时打开 |
| `info` | 正常业务流程的关键节点（请求开始/结束、状态变更） |
| `warn` | 可自愈的异常：重试成功、降级命中、参数不合法但已兜底 |
| `error` | 请求失败、依赖调用失败、数据异常 |
| `fatal` | 进程无法继续（极少用，多数情况是启动期失败） |

纪律：

- 生产环境默认级别 `info`；`warn` 以上都要能在仪表盘上被统计到。
- 不要用 `error` 记录「正常但少见的业务分支」——噪音会淹没真错误。
- 同一类失败的日志模板要稳定，方便 grep 和告警匹配。

### 禁止记录的内容

- 令牌、密码、API key、会话密钥——任何级别都不许。
- 完整身份证、手机号、银行卡号、地址等个人数据原文；需要时做哈希或脱敏，
  且脱敏规则要在日志规范里写明。
- 完整请求体中的敏感字段（密码框、支付信息）。
- 日志里打印大对象（整个 HTTP 响应、整个 ORM 对象）。

涉及用户数据的安全口径同步看 `skill://ecc-omp-security-review`。

## 指标口径

### counter / gauge / histogram 怎么选

- **counter**：只增不减的累计值。请求总数、错误总数、发送消息数。
  对外暴露的是「速率」（每分钟错误数），counter 本身只用于算差值。
- **gauge**：可上可下的瞬时值。队列长度、在线连接数、当前内存占用、缓存命中率。
- **histogram**：分布。延迟、响应大小。能算平均值，但看延迟**必须用分位**（p50/p95/p99），
  平均值会被长尾骗到。

选择口径：问「这个数是累计的还是瞬时的还是分布的」，答案直接对应三者之一。
需要看延迟/大小/耗时 → histogram；需要看当前水位 → gauge；需要算速率 → counter。

### 命名约定

格式：`<service>.<subsystem>.<metric>.<unit>`，全小写，点分。

| 指标 | 类型 | 说明 |
| --- | --- | --- |
| `checkout.orders.created_total` | counter | 下单成功总数 |
| `checkout.payment.duration_ms` | histogram | 支付耗时分布 |
| `checkout.cart.items_count` | gauge | 当前购物车商品数 |
| `checkout.http.requests_total` | counter | HTTP 请求总数（按 status_code 打标） |
| `checkout.http.errors_total` | counter | HTTP 5xx 总数，用于错误率 |

约定：`_total` 后缀留给 counter；gauge 不加后缀；histogram 用 `_ms`/`_bytes` 等单位后缀。

### 基数（cardinality）

基数 = 同一个指标名下不同标签值组合的数量。基数爆炸是指标系统被拖垮的头号原因。

典型原因与规避：

| 原因 | 后果 | 规避 |
| --- | --- | --- |
| 把 `user_id` 做成标签 | 每个用户一组序列，百万用户 = 百万序列 | 用户维度进日志和追踪，不进指标标签 |
| 把 `request_id`、`trace_id` 做成标签 | 每请求一序列 | trace_id 进日志，不进指标 |
| 把 `ip`、`device_id` 做成标签 | 海量组合 | 只做聚合（按地区）或不进标签 |
| 把动态参数值当标签 | 如 `?coupon=xxx` | 标签值必须是**有限枚举**：状态码、环境、服务名、错误码 |

口径：一个指标名的标签组合总数控制在几千以内。每个新标签上线前问一句
「这个值的取值范围是有限的吗」——无限的（ID、随机串）一律不进标签。

## SLO 与错误预算

### SLI 怎么定义

SLI 是可测量的指标表达式，常用三类：

- **可用性**：成功率 = `正常响应数 / 总请求数`（要明确「正常」的口径，如 HTTP 2xx，
  且排除健康检查、爬虫流量）。
- **延迟**：用分位，不看平均。`p95 延迟 < 500ms`，并按读/写、接口分别定义。
- **数据正确性/吞吐量**：按业务定，如「库存扣减零差错」「队列堆积 < 1 万条」。

### SLO 目标值怎么定

- 用错误预算倒推：想给用户 99.9% 可用性，错误预算就是 0.1%——一个月约 43 分钟故障时间。
- 新服务没有历史数据时：先宽松（99% 可用性）观察一个月，用真实数据校准，再收紧。
- 收紧 SLO 前必须确认错误预算用得上——目标定太高导致预算长期花不完，说明 SLO 没起到约束作用。

### 错误预算怎么用来决定「现在还能不能发布」

错误预算是燃料，发布会消耗它：

| 剩余预算 | 发布口径 |
| --- | --- |
| > 50% | 正常发布，带常规观察 |
| 20%–50% | 可以发布，但只带低风险变更，发布后加倍观察 |
| < 20% | 冻结非紧急发布；只做修复和回滚类变更 |
| 已耗尽（< 0% 或预算周期内超支） | 进入「稳定性模式」：暂停所有功能发布，只允许修复线上问题；复盘前不解除 |

错误预算耗尽时的决策口径：**先止血再复盘**。预算耗尽期的第一优先级是恢复服务，
不是发布新功能；复盘要回答「是预算定太松、还是系统真的不稳、还是发布流程引入了缺陷」，
三者对应不同动作（收紧 SLO / 修系统 / 改发布流程），不要混在一起。

## 告警设计

### 告警必须可执行

每条告警的注释里写清：**触发后执行什么动作**。对应不上任何 runbook 动作的告警删掉——
「看起来有用」的告警是噪音。runbook 至少包含：症状是什么、影响什么用户、
第一步做什么、升级路径。

### 按症状告警，不按原因告警

- 症状：用户可感知的失败——下单成功率下降、p95 延迟超限、错误率突增。
- 原因：CPU 高、内存涨、磁盘使用率——这些多数是**信息**，不是需要叫人的告警。
  CPU 高到导致症状时，症状告警会先响；CPU 高但服务正常，看仪表盘就够了。

例外：资源类告警在容量规划语境下有用（磁盘 95%），但要定成 ticket 级而不是 page 级。

### 金丝雀（5% 流量）期间的告警阈值

金丝雀阶段流量只有 5%，绝对值天然低：

- **不要**用绝对阈值（如「错误数 > 10」）告警——5% 流量下错误数很少也够阈值，或反过来。
- 改用**相对口径**：金丝雀组错误率 vs 对照组错误率，比值超限才告警；
  或「金丝雀组错误率 > X% 且持续 N 分钟」。
- 金丝雀告警的敏感度要高于全量阶段：同样症状，5% 流量时就该响，别等全量。

### 告警疲劳的抑制

- **分组**：同一根因引起的多条告警合并成一条（如下游故障导致上游 10 个接口报错）。
- **去抖**：触发条件加持续时长（「错误率 > 5% 持续 3 分钟」），避免瞬时毛刺叫人。
- **分级**：
  - `page`：用户可感知且需要立即处理——叫人，打断睡眠。
  - `ticket`：需要跟进但不紧急——工作时间处理。
  - `dashboard`：仅记录趋势——不发通知。
- 每周看一次告警触发统计：长期不触发的告警降级，频繁触发但没人处理的告警重新设计。

## 追踪接入

### trace_id 的生成与透传

- **入口生成**：服务最外层（网关/入口中间件）生成 trace_id，或从上游传来的头里取。
- **透传通道**（缺一个就断链）：
  - HTTP 调用：请求头（常见约定 `traceparent` 或自定义头 `X-Trace-Id`），出站请求必须带上。
  - 日志：每条日志带 `trace_id` 字段（见日志字段清单），日志和追踪通过它关联。
  - 消息队列：消息体或消息头里带 trace_id，消费端读取后继续传。
  - 异步任务/定时任务：任务启动时生成或继承 trace_id，写进任务上下文，子任务沿用。
- **跨服务传递**：每次出站调用（HTTP、RPC、MQ、异步任务）都要把当前 trace_id 带到下一跳；
  下游收到后写进自己的日志和出站调用。

### 常见断链原因

| 断链原因 | 症状 | 修法 |
| --- | --- | --- |
| HTTP 客户端没透传头 | 下游日志里 trace_id 缺失或变成新生成的值 | 检查所有出站调用的拦截器/中间件 |
| 消息队列没带 trace_id | 消费者侧日志对不上生产者 | 消息头加字段，消费端读入上下文 |
| 异步线程池丢失上下文 | 后台线程日志 trace_id 为空 | 线程池用装饰器/上下文变量传递 |
| 定时任务每次不生成新 id | 定时任务之间 trace_id 相同，无法区分批次 | 每批次生成新 trace_id，或加批次号 |
| 日志中间件没注入字段 | 日志里根本没有 trace_id 列 | 日志格式化层统一注入，不要各服务手写 |

## 操作步骤

给新服务接入可观测性的最小步骤：

1. **日志**：统一 JSON 格式，注入字段清单里的字段；定日志级别纪律；写明脱敏规则。
2. **指标**：选定命名约定，先上 4 条核心指标——请求总数、错误总数、延迟分布、
   队列/连接数（gauge）。基数按上面的口径自查。
3. **追踪**：入口生成 trace_id，配置日志注入、HTTP 头透传、MQ 透传；
   上线后用「构造一次跨服务请求，在追踪系统里能完整看到链路」作为验收。
4. **告警**：先定 SLO，再定告警；每条告警对应一个 runbook 动作；分级 page/ticket/dashboard。
5. **验证**：发布前跑 `skill://ecc-omp-verification-loop` 的验证闭环时，
   把「新告警能触发、新指标有数据、trace_id 能串链」纳入验证清单。

## 查询样例

以下查询是通用表达，具体语法以你的可观测平台为准（日志平台、指标系统、追踪系统、
告警平台各自不同）。命令行示例用 `bash` + `grep` 表达日志检索的通用形态。

1. **按 trace_id 检索日志**：拿到一个 trace_id，把这次请求在各服务产生的日志全捞出来。
   `grep 'trace_id=a3f9e21' app.log`（或在日志平台按 `trace_id` 字段过滤，选时间窗口）。
2. **查某服务的 p95 延迟分位**：在指标系统查
   `histogram 分位函数(checkout.payment.duration_ms)`，按 `p95` 聚合，看时间范围趋势。
3. **查错误率突增的时段**：用错误 counter 和总请求 counter 算速率比
   `rate(checkout.http.errors_total) / rate(checkout.http.requests_total)`，按时间轴找峰值时段。
4. **看某个告警最近触发记录**：在告警平台查该告警名的最近 N 次触发时间、持续时长、关联对象。
5. **grep 日志里某错误码**：`grep 'error_code=PAYMENT_TIMEOUT' app.log | head`，
   配合时间窗口定位首次出现时间。
6. **导出某段时间的指标做对比**：导出 UTC 某小时的 `checkout.orders.created_total`
   速率曲线与上周同期对比，看是否回归。

## 判定口径

上线前逐条自检（可做成检查清单）：

- 日志：每条生产日志有 `timestamp` / `level` / `trace_id` / `service` / `env` / `event`；
  抽查无令牌、无完整个人数据原文。
- 指标：核心 4 条（请求、错误、延迟分布、水位）有数据且曲线连续；
  每个指标名的标签组合数 ≤ 几千。
- 追踪：跨服务请求能在追踪系统看到完整链路；MQ/异步任务链路不断。
- SLO：每个用户可见接口有 SLI 定义和目标值；错误预算表贴在发布流程里。
- 告警：每条告警能说出「触发后做什么」；page 级告警都是症状类；
  金丝雀告警用相对口径；所有告警有分级。
- 发布决策：错误预算耗尽期发布冻结，只看修复类变更。

## 反模式清单

1. **日志当数据库用**：在日志平台写复杂 JOIN、做报表、存业务状态。日志是排查用的，
   业务状态去数据库和指标里查。
2. **无 trace_id 导致链路断掉**：出问题后靠时间戳和关键字手工拼各服务日志。
   trace_id 是串链的唯一可靠手段，缺了就等于没有追踪。
3. **给每个用户 ID 打标签导致指标爆炸**：`user_id` 进指标标签，序列数随用户量线性涨，
   把指标系统拖垮。用户维度进日志和追踪。
4. **按 CPU 阈值告警而不是按用户症状告警**：CPU 90% 但用户无感知，深夜叫人；
   用户下单失败但 CPU 正常，没人叫。症状告警优先，资源水位降级为 ticket。
5. **没有 runbook 的告警**：告警响了没人知道该干什么，要么乱操作要么忽略。
   对应不上动作的告警删掉。
6. **指标口径改名字不断历史曲线**：把 `duration` 改名 `duration_ms` 或换口径后不标注，
   历史曲线断档，趋势对比失真。改名要带迁移说明，或先双写过渡再切换。
7. **平均值看延迟**：p50 稳定但 p99 爆炸，平均值看不出来。延迟一律看分位。
8. **金丝雀阶段用绝对阈值**：5% 流量下「错误数 > 10」要么不响要么乱响，
   必须用相对口径（与对照组比值）。
