# 代码风格（fork 专属）

上游 ECC 的 `coding-style` 是一份通用风格清单。这里只保留真正影响日常判断的几条，
并补上「跟随项目既有风格」这个前置原则。

## 前置：跟随项目

**先看这个仓库怎么写的，再写你的代码。** 具体表现为：

- 命名风格（`snake_case` / `camelCase`）、目录布局、错误处理方式、测试写法，
  以仓库现有代码为准。
- 同一个概念在项目里已有叫法，就用它；不要引入平行的第二套叫法。
- 项目有 lint / format 配置就照它执行，不要手工争论格式。

上面所有"通用原则"都排在这一条之后。

## 不可变优先

不要就地修改传入的对象，返回新值：

```
// 反例：修改原对象
modify(record, "status", "done")        → 原地改了 record
// 正例：返回新对象
update(record, "status", "done")        → 新副本
```

理由：不可变数据没有隐藏副作用，调试容易，也天然避免并发写冲突。
例外：明确的可变数据结构（`ArrayList`、DOM 节点、构建器自身）在其抽象内修改是正常的。

## 简单优先

- 选**能跑通的最简方案**。不要为假想的将来做抽象。
- 清晰优先于巧妙。聪明到需要解释的代码，通常有更直白的写法。
- 但也别过度简化到丢掉了必要的错误处理和边界检查。

## DRY 的边界

重复出现**三次以上**、且每次都要同步修改的逻辑，才值得提取。
只重复两次的相似代码，先按字面写清楚，等第三次再抽象。
（fork 自定的具体次数，上游只说「repetition is real, not speculative」，没给数字。）

过早抽象的代价通常高于重复：抽错的抽象会把错误固化到多个调用点。

## 注释

注释写**为什么**，不写**是什么**。注释的作用是解释意图，不是复述代码；
写不出有信息量的注释时，就别写。（fork 自定，上游 `coding-style` 没有 Comments 章节。）

```
# 反例：给函数起名后再说一遍函数名
# increment counter 计数器加一
# 好：解释这个 +1 的业务含义
# 配额从下个自然月开始算，所以这里先补当月
```

- 改代码时同步更新过期注释。
- 被注释掉的代码块直接删掉，交给 git 历史。

## 错误处理

- 不要静默吞错。捕获异常后要么处理、要么重新抛出并附带上下文。
- 不要用宽泛的兜底默认值掩盖问题（比如解析失败就返回空对象）。
- 日志里不要输出敏感信息。
